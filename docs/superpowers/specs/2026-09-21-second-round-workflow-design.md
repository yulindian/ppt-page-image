# PPT Page Image 第二轮工作流改造设计

## 背景

第一轮已经建立了外部工作区、Schema v2、四级门禁、策划文件单一数据源和干净交付晋级机制。当前主要风险不再是缺少规则，而是正常生产仍需人工创建目录、编辑大段 JSON、手动维护状态与审核失效关系。文档要求已经严格，但操作者仍可能因为漏改字段、错用旧审核或跳过步骤而产生不一致状态。

第二轮把这些规则转化为确定性的项目操作工具，同时保持“过程文件永不进入最终交付目录”这一核心约束。

## 目标

1. 新项目能够通过一个命令生成可工作的标准工作区与状态文件。
2. 正常推进、内容修改、视觉修改和审核记录不再依赖直接编辑状态 JSON。
3. 页面图片变化会自动废止所有依赖旧哈希的下游审核证据。
4. 操作者可以通过一个检查命令知道当前状态、可执行的下一步和具体缺项。
5. 页面、家族、整套和 PDF 审核均保存结构化、与哈希绑定的证据。
6. 自动预检覆盖机器可以可靠判断的技术问题；OCR 仅报告风险，不替代人工视觉检查。
7. 新项目具备来源追溯、操作日志和最终交付清单。
8. Schema v1/v2 项目保持可读取，并能迁移到新版本。
9. 主 Skill 入口更短，详细规则按任务路由加载。

## 非目标

- 不创建可编辑 PPTX，也不改变完整页面图片 PDF 的交付形态。
- 不用 OCR 自动判定中文文案绝对正确。
- 不自动调用图像生成模型重试页面。
- 不覆盖或重写既有用户交付目录中的非托管文件。
- 不在本轮引入数据库、后台服务或第三方云依赖。

## 方案选择

采用“共享状态核心 + 小型命令行工具”的模块化方案。

不采用单一全能脚本，因为初始化、状态变更、审核和交付具有不同失败边界；一个命令承担全部职责会使回滚和测试困难。也不继续在现有脚本中分别复制 JSON 处理逻辑，因为路径检查、原子写入、哈希和状态顺序一旦分叉，会重新形成多个事实来源。

## 架构

### 共享核心

新增 `scripts/project_state.py`，集中提供：

- UTF-8 JSON 读取与规范化写入；
- 临时文件加原子替换的安全保存；
- 工作区内相对路径解析与越界阻止；
- 文件 SHA-256；
- 状态顺序和允许的推进、回退关系；
- 页面、家族、整套、渲染审核的依赖失效；
- 操作日志追加；
- Schema 版本识别。

现有 `validate_project.py`、`generate_planning_files.py` 和新增命令逐步改用该核心。验证器仍只读，不在失败时偷偷修改项目状态。

### 命令行工具

#### `init_project.py`

输入课件名、页数、受众、场景和工作区，创建：

```text
<workspace>/
|-- project-state.json
|-- planning/
|-- fonts/
|-- slides/
|-- samples/
|-- montages/
|-- reports/
|-- render-back/
`-- history/
```

新目录必须为空或不存在。命令不得接管包含用户文件的目录。初始状态为 `INTAKE`，页面只建立编号占位，不伪造已完成的文案、提示词、字体或审核信息。

#### `update_project.py`

提供明确子命令，而不是任意 JSON Patch：

- `apply-plan`：从独立的结构化计划文件更新 deck、style、fonts、sources、enrichment、families 和 pages；先完整验证，再一次性原子写入，禁止部分成功。
- `set-status`：只允许合法推进；进入目标阶段前检查除“当前状态值”以外的目标门禁条件，写入后再执行完整门禁验证。
- `register-image`：登记页面当前图片及哈希，并废止依赖旧图的审核。
- `content-changed`：记录内容变更原因，回退至 `PLANNING_READY`，废止策划文件登记和全部生产审核。
- `visual-changed`：记录页面和原因，回退至最早受影响阶段，废止页面、家族、整套和渲染审核。
- `record-review`：写入页面、家族、整套或渲染审核结果及证据。

每次成功操作使用原子写入，并追加包含时间、动作、目标和原因的 `audit_log`。失败操作不修改文件。

#### `project_check.py`

运行当前状态适用的结构检查和门禁检查，输出：

- Schema 版本与当前状态；
- 已满足的最近门禁；
- 当前缺项；
- 建议的下一条命令；
- JSON 模式，供测试和其他脚本稳定消费。

检查命令返回值：完全可继续为 `0`，存在阻塞项为 `1`，输入或环境错误为 `2`。

### Schema v3

新项目默认使用 `schema_version: 3`。v3 保留 v2 的 `deck`、`style`、`fonts`、`enrichment`、`families`、`pages`、`reviews` 和 `delivery`，增加：

- `sources`：来源 ID、类型、路径或网址、文件哈希、获取日期、权利状态和备注；
- 页面 `source_refs`：引用来源 ID；
- `reviews.pages`：逐页审核结果、页面哈希、检查项、备注和时间；
- 家族审核的 Montage 路径与哈希；
- 整套审核的 Montage 路径、哈希和成员页面哈希；
- 渲染审核的 PDF 哈希、逐页渲染哈希和检查项；
- `audit_log`：只追加的操作记录；
- `delivery.manifest`：最终清单文件名和登记项。

审核通过必须绑定当时的输入哈希。只要输入哈希变化，对应审核立即失效；不能只靠状态字符串继续通过门禁。

### 迁移

新增 `migrate_project.py`：

- v2 可确定映射为 v3 的字段自动迁移；缺失的新审核证据标记为待补，不伪造通过结果。
- v1 先映射到兼容的 v3 基础结构；无法确定的字段进入 `migration_warnings`，状态不高于 `PLANNING_READY`。
- 默认写入新文件；只有显式 `--in-place` 才原子替换原状态，并在工作区 `history/` 保存旧文件副本。
- 重复迁移同一 v3 文件不改变内容。

## 审核证据

### 自动预检

新增 `preflight_images.py`，对页面目录生成 JSON 报告并检查：

- 文件是否可打开；
- 编号是否连续、页数是否匹配；
- 尺寸和 16:9 比例；
- 空白或近空白页；
- 完全重复图片；
- 四边异常白边或透明边；
- 最低像素尺寸；
- 与项目状态登记哈希是否一致。

阈值写入报告，命令参数可覆盖。预检结果只判断技术问题，不对审美质量作自动通过结论。

OCR 设计为可选适配器：环境中存在受支持引擎时输出识别文本与锁定文案差异；没有 OCR 引擎时报告 `unavailable`，不会误报门禁通过，也不会成为初始化的强制依赖。

### Montage

新增 `build_montage.py`，支持 `--family <name>` 和 `--deck`。输出图片及伴随 JSON，记录成员页码、成员哈希、布局列数、生成时间和 Montage 哈希。任何成员哈希变化后，旧 Montage 不能用于审核通过。

### 人工审核

`record-review` 要求人工明确提交检查项。页面审核至少覆盖文案、层级、裁切、清晰度、伪文字和风格；家族审核覆盖固定组件、允许变化和禁止漂移；整套审核覆盖顺序、节奏、重复与整体一致性；渲染审核覆盖 PDF 页面数、边缘、裁切、清晰度和颜色。

失败审核可以保存，但不能推进状态。通过审核时所有输入文件必须存在且哈希匹配。

## 来源追溯

来源统一登记后，页面和补充材料只引用来源 ID。验证规则包括：

- 页面引用的来源必须存在；
- 本地来源文件存在时哈希必须匹配；
- 用于事实或真实照片的来源必须有日期和权利状态；
- 已接受的补充材料必须引用至少一个来源；
- 来源文件仍属于过程材料，不进入最终目录，除非被明确登记为可交付图片素材。

## 最终交付清单

`promote_delivery.py` 在暂存目录生成 `交付清单.json`。清单包含：

- Schema 和清单版本；
- 课件名与页数；
- PDF、三份策划文件、字体和可选图片的相对路径、字节数与 SHA-256；
- 最终验证时间；
- PDF 渲染审核哈希。

清单是最终成品的一部分，不包含工作区绝对路径、候选稿、审核截图或状态文件。最终验证器重新计算清单中的全部哈希，并拒绝未登记文件和缺失文件。

## Skill 文档结构

`SKILL.md` 只保留触发条件、生产契约、阶段路由、不可越过的门禁和交付定义。具体字段、命令和检查表继续放在对应 references 中。相同规则只保留一个权威版本，入口文件通过明确的“何时读取”链接路由。

`tests/behavior-scenarios.md` 中的关键行为转成可执行集成测试，包括：

- 初始化 26 页项目；
- 用户指定前五页作为试做页；
- 修改单页后仅相关页面与家族审核失效；
- 内容修改后策划及下游审核全部失效；
- 第二次交付不会把旧稿带入最终目录；
- v1/v2 迁移不伪造审核通过；
- 工作区或交付路径包含中文和空格。

## 兼容性与错误处理

- 保持现有 v1/v2 验证入口可用；v3 使用同一 `validate_project.py` 门禁接口。
- CLI 成功信息写标准输出，错误写标准错误，并使用稳定退出码。
- 所有写操作先验证后写入；保存失败不得留下截断 JSON。
- 所有路径在使用前解析，工作区内产物不得通过 `..`、符号链接或大小写差异逃逸。
- 不自动删除用户文件；历史清理由用户明确发起。
- Windows 为主要运行环境，同时避免依赖 PowerShell 特有的路径字符串，使 Python 脚本可在其他平台测试。

## 实施分段

1. 共享状态核心、Schema v3、初始化和迁移。
2. 状态推进、修改失效和一键检查。
3. 自动预检、Montage 和结构化人工审核。
4. 来源追溯、交付清单、文档瘦身和完整回归场景。

每段独立测试、独立提交。实现阶段在隔离工作树中进行；完成后先保留功能分支，不自动合并或推送。

## 验收标准

- 从空目录初始化一个 26 页中文项目无需手工创建结构。
- 正常状态变更和审核登记无需直接编辑 JSON。
- 替换任意页面图片后，使用旧哈希的页面、家族、整套和渲染审核无法通过。
- 一键检查能给出稳定、可操作的缺项和下一步建议。
- v1/v2 项目可迁移，且不会因为迁移获得虚假的审核通过状态。
- 最终目录只包含 PDF、三份策划文件、字体、可选登记图片和 `交付清单.json`。
- 交付目录内任一文件被替换后，验证失败。
- 现有 61 项测试继续通过，新增功能具备 RED→GREEN 回归测试。
- 使用现有《让班级升温》项目副本完成一次兼容性演练，不覆盖原交付目录。
